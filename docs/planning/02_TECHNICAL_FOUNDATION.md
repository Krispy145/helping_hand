# Technical Foundation & Architecture Strategy

**Goal:** Establish a scalable, automated, and type-safe foundation for the Helping Hand monorepo.

---

## 1. Monorepo Structure
We will use a simplified Monorepo structure to house the Flutter App, NestJS API, and the Web Dashboard.

```text
helping_hand/
├── apps/
│   ├── mobile/          # Flutter App (iOS/Android)
│   ├── api/             # NestJS Backend
│   └── web_pulse/       # Flutter Web Dashboard (Humanity Pulse)
├── packages/            # Shared Code (Dart/Flutter)
│   ├── models/          # Shared DTOs, Entities, and dart_mappable logic
│   └── ui/              # Shared Design System (Colors, Typography, Widgets)
├── docs/                # Project Documentation
├── tooling/             # Shared scripts / git hooks
└── .github/             # CI/CD Workflows
```

## 2. Frontend Architecture (Mobile & Web)

### Core Patterns
- **Architecture:** Feature-First (Layered).
    - `features/auth/` (presentation, application, domain, data)
    - `features/chat/`
- **Shared logic:**
    - `packages/models`: Shared DTOs (Mobile/Web/API parity).
    - `packages/ui`: Shared Design System (Design tokens, reusable widgets).
- **State Management:** **Riverpod** (Used in both apps).

### Localization Strategy (i18n)
- **Tool:** **Slang** (formerly `fast_i18n`).
- **Why:**
  - Type-safe generation (`t.welcomeMessage`).
  - **JSON/YAML support:** Key for your requirement to eventually migrate to Remote Config / Backend JSON.
  - No context required in logic.
- **Workflow:**
  - `i18n/strings_en.i18n.json` (Source of Truth).
  - Generator creates `Strings` class.
  - Code uses `t.common.ok`.

### Theming Strategy (Design System)
- **Location:** `packages/ui`.
- **Pattern:** **Theme Extensions** (Official Flutter best practice).
  - Don't just rely on `ColorScheme`. Create `AppColors` and `AppTextStyles` extensions.
- **Remote Theming Ready:**
  - Because we define our own `AppThemeExtension` class, we can easily add a method `AppThemeExtension.fromJson(...)` later to hydrate the theme from a remote Backend response, allowing dynamic rebranding.

### Mobile Specifics
- **Deep Linking:** `go_router` (`helpinghand://`, `https://helpinghand.com`).
- **Notifications:** FCM Native.

### Web Dashboard Specifics (`apps/web_pulse`)
- **Hosting:** **Firebase Hosting**.
- **Analytics:** Aggregated "Humanity Pulse" data.

### Flavors & Environment Strategy
*Using `flutter_flavorizr` (Mobile) + Build Args (Web)*

| Feature | **Dev Flavor** | **Staging Flavor** | **Prod Flavor** |
| :--- | :--- | :--- | :--- |
| **Backend** | **Localhost** (10.0.2.2) | **Staging Cloud** (Cloud Run) | **Prod Cloud** (Cloud Run) |
| **Mobile Updates** | USB Install | **Shorebird** (Private Channel) | Store / Shorebird |
| **Web Hosting** | `localhost:8080` | `stg.pulse.helpinghand.com` | `pulse.helpinghand.com` |

## 3. Backend Architecture (NestJS)

### Core Patterns: SOLD & SOLID
To ensure the backend remains database-agnostic (switching providers later) and testable:

- **Repository Pattern (Dependency Inversion):**
  - **Interface:** `IUserRepository` (Domain).
  - **Implementation:** `PrismaUserRepository` (Data).
- **Notifications Abstraction:**
  - **Interface:** `INotificationService`
  - **Implementation:** `FcmNotificationService`

- **Database:** Postgres + **Prisma ORM**.
- **Queue System:** **BullMQ** (Redis).

## 4. Deployment & CI/CD Strategy (Detailed)

### Mobile Workflow (Shorebird + Fastlane)
Shorebird determines *how* we build, and Fastlane determines *where* we deliver.

#### A. The "Store Release" Workflow (Native Changes)
*Trigger: Git Tag `v1.2.3`*
1.  **CI (GitHub Actions):** Checkout code.
2.  **Shorebird Build:** Run `shorebird release android --flavor prod` and `shorebird release ios --flavor prod`.
    *   *Why Shorebird here?* You MUST use Shorebird to build the initial release binary. If you use standard `flutter build`, Shorebird cannot patch it later because it lacks the Shorebird engine.
3.  **Fastlane:**
    *   Takes the `.aab` (Android) and `.ipa` (iOS) generated by Shorebird.
    *   Uploads to **Google Play Console** (Internal Track) and **TestFlight**.
4.  **Result:** A new version is visible in the App Stores.

#### B. The "OTA Patch" Workflow (Dart-only Changes)
*Trigger: Push to `main` (for Staging) or Manual Dispatch (for Prod)*
1.  **CI (GitHub Actions):** Checkout code.
2.  **Validation:** Check if any Native code (Kotlin/Swift/Gradle/Podfile) changed. If yes => FAIL (Must do Store Release).
3.  **Shorebird Patch:** Run `shorebird patch android --flavor prod` and `shorebird patch ios --flavor prod`.
4.  **Result:** Users with the app installed download the update in the background. **No App Store review needed.**

### Web Pulse Workflow
- **Staging:** GitHub Action -> `flutter build web` -> `firebase deploy --only hosting:staging`.
- **Prod:** GitHub Action -> `flutter build web --release` -> `firebase deploy --only hosting:prod`.

### Backend Workflow
- **Staging/Prod:** GitHub Action -> Docker Build -> Cloud Run.
